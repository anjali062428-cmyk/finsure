## 1. Executive Summary

Phase 8 implements the complete backend investigation foundation for FinSure, delivering the **Investigation Workspace** data model and the **FinSure Investigator** assistive intelligence service.

Strict adherence to the FinSure SRS and Master Prompt was maintained throughout:
1. **Human Authority Maintained:** The AI/LLM system never decides fraud verdicts, alters transaction states, or blocks users.
2. **Read-Only Sandbox Enforced:** The Investigator operates in an execution sandbox with whitelisted read tools only; all write operations raise `PermissionError`.
3. **100% Evidence-Grounded:** Every narrative claim generated by the Investigator must cite valid `[E...]` evidence IDs and match evidence metadata; ungrounded statements are rejected with automatic fallback to deterministic templates.
4. **Immutable Evidence Store:** Evidence items are never deleted; erroneous items can only be marked `withdrawn` with a mandatory reason.
5. **Four-Eyes Governance:** Dismissing a `CRITICAL` priority case requires mandatory approval by a second analyst or administrator.

## 2. Architecture & Components Built

### 2.1 Canonical Case Entity & State Machine (`backend/models/case.py`, `backend/services/case_service.py`)
- **Decoupled Case Model:** Separates operational triage and analyst dispositioning from raw incidents:
  `case_id, incident_id, alert_id, transaction_id, user_id, status, priority, risk_score, risk_band, decision, scam_type, assigned_to, sla_due_at, customer_reported, opened_at, updated_at, closed_at, closed_by, disposition, disposition_reason, disposition_note, created_by`.
- **Formal State Machine Matrix:**
  $$\text{new} \longrightarrow \text{under\_investigation} \longrightarrow \{\text{escalated}, \text{confirmed\_fraud}, \text{dismissed}\} \longrightarrow \text{closed}$$
- **Four-Eyes Policy:** Regular analysts cannot unilaterally dismiss `CRITICAL` priority cases without `approved_by` populated with a distinct second analyst or administrator.
- **Customer Fast-Path:** Customer "Not me" reports directly create cases flagged with `customer_reported=True`.

### 2.2 Immutable Case Evidence Store (`backend/repositories/case_repo.py`)
- Supports diverse forensic evidence types: `transaction`, `device`, `location`, `shap_reason`, `autoencoder_anomaly`, `graph_link`, `user_profile`, `external_file`, `analyst_note`, `customer_report`.
- Computes SHA-256 content hashes for all evidence payloads.
- **Never Deleted:** Soft-withdrawal via `withdrawn_at` and `withdraw_reason`.

### 2.3 Read-Only Investigator Tool Sandbox (`backend/services/tool_sandbox.py`)
- **Whitelisted Read Tools:** `get_case`, `get_incident`, `get_evidence`, `get_timeline`, `get_report`, `get_similar_cases`, `verify_audit_chain`, `get_transactions`, `get_user_profile`, `get_devices`, `get_locations`, `get_linked_accounts`, `get_shap`.
- **Prohibited Write Tools:** `create_case`, `update_case`, `change_status`, `modify_risk_score`, `modify_threshold`, `block_transaction`, `dismiss_incident`, `confirm_fraud`, `delete_evidence`, `modify_user`, `add_feedback`, `record_transition`, `update_alert`. Attempted calls raise `PermissionError`.

### 2.4 PII Masker & Prompt Injection Defense (`backend/services/pii_sanitizer.py`)
- Masks phone numbers (`+91 *** *** 3210`), emails (`al***@example.com`), VPAs (`me***@okaxis`), IPs (`103.87.x.x`), and device fingerprints.
- Scans untrusted input strings for jailbreaks, prompt override commands, or SQL patterns.
- Wraps untrusted user/payee inputs in strict `<UNTRUSTED_DATA>` boundaries.

### 2.5 Claim Validation Engine (`backend/services/claim_validator.py`)
- Evaluates draft narrative text against active case evidence.
- Extracts citation tags (`[E1]`, `[E2]`).
- Rejects non-existent or withdrawn evidence references.
- Validates numerical amounts (e.g. `₹25,000`) and device identifiers against cited metadata.
- Rejects autonomous verdict assertions (`"100% confirmed fraud"`, `"User is guilty"`).
- Computes groundedness ratio; enforces 100% pass rate.

### 2.6 FinSure Investigator Service (`backend/services/investigator_service.py`)
- Named **"FinSure Investigator"** (calm branding).
- Executes structured Plan:
  1. Retrieve case details & risk scoring profile.
  2. Examine transaction details, amount, channel, and velocity.
  3. Examine device fingerprint and IP telemetry.
  4. Examine SHAP explainability feature impacts.
  5. Examine deep autoencoder reconstruction error.
  6. Examine entity graph links and shared payees.
  7. Evaluate missing evidence checklist.
- Generates structured, evidence-cited forensic findings using `TemplateInvestigatorAdapter` by default.
- If a model adapter introduces an unsupported claim, automatically triggers instant fallback to the deterministic template.
- Persists every run in `investigation_runs`.

### 2.7 Evidence Pack Exporter (`backend/services/case_service.py`)
- Generates a standalone, court-ready `.zip` archive containing:
  - `manifest.json` with SHA-256 hashes of all bundled files.
  - `case_summary.json`
  - `evidence_records.json`
  - `audit_events.json`
  - `case_transitions.json`
  - `investigation_report.txt`

## 6. Known Limitations
- The current implementation defaults to the `TemplateInvestigatorAdapter`, which is 100% grounded and deterministic. Integration with optional local Ollama or hosted LLM endpoints is fully supported via the `InvestigatorModelAdapter` interface, but external network LLM calling is disabled in test/offline mode.
- Exported evidence packs include JSON forensic records, transitions, audit chains, and text investigation reports; integration with PDF evidence packs reuses Phase 7 `IncidentReportService` artifacts.
